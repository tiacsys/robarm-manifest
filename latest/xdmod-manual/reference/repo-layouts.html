Repo layouts

Every repo that uses XDMOD follows one common pattern. Domain repos add their own folders. Examples are from the robot arm.

Common pattern

<repo>/
  README.md
  checks.yaml            what `curatrix check` runs for this repo
  ids.yaml               ID ledger
  requirements.txt       pinned pip packages this repo needs
  tools.yaml             pinned non-pip tools (name, version, source, sha256)
  docs/
    documents.yaml       zdocs registry: own documents and upstream documents
    CMakeLists.txt
    <doc-id>/            one folder per document (conf.py and rst)
  generated/             committed generated files, checked by `curatrix check`
  claude/                agent material for this repo
  .github/
    workflows/           thin callers of the reusable workflows in xdmod
    pull_request_template.md
  .gitattributes         diff drivers (e.g. *.FCStd diff=fcstd -merge)

Rules:

  • No build output in repos (Build output only under build/ (XD-RULE-0040), no build output inside the ... (XD-CHECK-0026)). Everything goes to <workspace>/build/<area>/ (Every check also runs locally (XD-ADR-0040)). <area> is the repo name, full for the full set, the branch for worktree builds (Parallel agents work in git... (XD-ADR-0114)), or a named step.

  • Generated files are committed only in generated/, except where the tool needs them next to the source: SysML stubs in model/generated/ and views in views/.

  • Folder names are lowercase with dashes. Each PCBA, assembly and configuration gets its own folder, so adding one never moves another.

Systems engineering repo

model/                  *.sysml per SYSMOD step (see the SYSMOD mapping)
model/generated/        stubs from the needs
views/                  <view>.drawio.svg
generated/              model.json, model-needs.json
docs/se-req/  docs/se-arch/

EE repo

model/                  EE domain model: board defs, connector port defs with pin maps,
                        cable defs, external parts, board variants
pcba/<name>/            one KiCad project per board def: <name>.kicad_pro, schematic, board,
                        library tables, <name>.kicad_jobset, accepted.yaml
proto/<name>/           one KiCad project per block of the prototype configuration
harness/<name>/         one WireViz harness per cable def: <name>.yml
lib/                    project-local symbols, footprints, 3D models
tests/                  scripted EE checks, JUnit output
generated/              cad-needs.json, model.json, <project>.connectors.json
docs/                   ee-req, ee-design, ee-test-spec, ee-test-report; harnesses
                        (every cable); pcbas/pcba-<name>/ (one per board); prototype
                        projects (proto-<name>)

KiCad library tables refer to the shared libraries only through variables (${XD_KICAD_SYMBOLS} and so on) and to lib/ through ${KIPRJMOD}. curatrix launch kicad sets the variables (Pinned, isolated component ... (XD-ADR-0080)). The domain model owns the board, port and harness IDs; KiCad and WireViz files refer to them (The domain model owns the I... (XD-ADR-0128)): a KiCad project by its TraceID text variable, a WireViz harness by metadata: {TraceID: EE-HAR-....}, and each of its connectors by three lines in its notes that name the end port of the cable def, as a KiCad connector’s fields name the port of its board def: portName: boardEnd, portType: CanaryHeader, portTypeID: EE-PORT-0001 (the def is also the port it mates with, on a board or an external part; WireViz shows the notes in the diagram; portName: - for none). Port usages have functional names, and board connectors the designator prefix X (Ports have functional names... (XD-RULE-0066)). The connector’s pins and pinlabels are the pin numbers and net names of that port’s pin map; the pin maps at both ends use the same net names (the pin map of a bought part names its pins with our nets, not the vendor’s). The cable def has one port per end, typed by the (conjugated) port def it mates with; EE-HAR connects EE-PORT comes from these ports (one target for a cable with the same port def at both ends; CK-F1 counts the ends). The jobset is a copy of the xdmod template (EE design output in iterati... (XD-ADR-0142)); accepted.yaml holds the accepted ERC and DRC findings (One accepted.yaml format, w... (XD-ADR-0126)). There is one document per board, prototype project and harness (One document per board, har... (XD-ADR-0129), WireViz for harnesses (XD-ADR-0127)).

ME repo

model/                  ME domain model: assembly defs, mechanical port defs, variants
parts/<part>.FCStd      shared parts, stored uncompressed
assemblies/<name>/      <name>.FCStd (top document), skeleton.FCStd (parameters, variant
                        table, master sketch), parts/, accepted.yaml
lib/                    project-local parts
templates/              TechDraw templates
print/                  print-settings profiles
tests/                  scripted ME checks, JUnit output
generated/              cad-needs.json, model.json, semantic JSON of each .FCStd
docs/                   me-req, me-design, me-test-spec, me-test-report;
                        assemblies/asm-<name>/ (one per top-level assembly)

FreeCAD files are stored uncompressed, with a git textconv for readable diffs (FreeCAD files uncompressed,... (XD-ADR-0056), Design files are stored unc... (XD-RULE-0039)). Parts refer only to the skeleton, never to the top document (FreeCAD assemblies: a skele... (XD-ADR-0137)). Board models come at fixed versions from a board library repo (A board library repo for ME (XD-ADR-0139)). Boards, harnesses and assemblies have their own tags <name>/vX.Y.Z, made by the owner only (Tags per board, assembly an... (XD-ADR-0140)).

Board library repo

boards/<board>/<board>-<vX.Y.Z>[-<variant>].FCStd
                        one FreeCAD model per tagged board version and variant: board body and
                        components, no tracks; App::Part "Board" with TraceID (EE-PCBA),
                        Version, Variant, Commit; uncompressed; at most 5 MB; never replaced
docs/                   board-library: the list of board versions, made from the files
checks.yaml             board_library: {source: "{ws}/<ee repo>"} (CK-F20); no ids.yaml

A top-level west project in the west groups of EE and ME (A board library repo for ME (XD-ADR-0139)). EE writes a tagged board version with curatrix cam <ee repo> <board> --library and opens the pull request; ME links one fixed version, and cad.board_library in the ME repo’s checks.yaml notes a newer one (CK-F21).

SW repo

app/                    the firmware application
dts/bindings/           the project's own devicetree bindings, with trace-id
tests/<suite>/          unit and hardware test suites, with test IDs from the ledger
docs/                   SW requirements, architecture and design, API (Doxygen),
                        test spec, test report; firmware/fw-<name>/ (one per image)

SW architecture is written in rst in iteration 1 (SW architecture in rst in i... (XD-ADR-0069)). Test reports are separate documents from the test specs (Test reports are separate d... (XD-ADR-0099)).

Per-deliverable documents sit in one sub-folder of docs/ per kind (pcbas/, assemblies/, firmware/); their registry entry names the folder (doc_dir: pcbas/pcba-<name>), their ID and Pages path stay flat (html/pcba-<name>/). CK-A7 checks the layout (V-model documents for EE an... (XD-ADR-0149)).

Integration repo

tests/                  system and integration test cases
hil/<setup>/            HIL setups: hardware map, fixtures, runner config
docs/                   system and integration test spec and report
branch `evidence`       orphan branch with HIL run records, never merged

Every test that verifies a system requirement or interface lives here (Tests live by what they verify (XD-ADR-0104)).

west.yml                imports submanifests/
submanifests/*.yml

docs/                   full-set registry and the project overview document
.github/workflows/      bump bot, full-set build, Pages publishing

xdmod

claude/                 planning folder and shared agent material: skills, commands, checklists
launch/CLAUDE.md        launch file, copied to the workspace root by the bootstrap
curatrix/               the tool (Python package)
sphinx/                 Sphinx extensions and the shared conf helper

sysml/                  SysML library: trace metadata, @XdView

workflows/              reusable GitHub workflows
docs/xdmod-manual/  docs/xdmod-ref/
