Framework Decision: EE design output in iteration 1 XD-ADR-0142
status: valid
date: 2026-11-17
decision_status: accepted
refines: XD-ADR-0018
revises: XD-ADR-0037
decides: XD-RULE-0053, XD-RULE-0054

The EE part of the CAM pipeline moves into iteration 1. curatrix cam <repo> [<project>] copies the KiCad project into build/<repo>/cam/<project>/<version>/, writes the version into the copy’s .kicad_pro text variable XD_VERSION and runs the jobset there with kicad-cli jobset run. The committed project keeps XD_VERSION = "unversioned".

  • Version: git describe --match '<project>/*' (Tags per board, assembly an... (XD-ADR-0140)). A dirty tree, or a commit that is not on main or a baseline, gives a version marked as preview; without a tag it is <project>/v0.0.0-<n>-g<sha>-preview. The full version goes into a title-block comment line and a silkscreen text; the Rev field cuts long strings off, so it holds only the short version or nothing.

  • Jobset: one shared template in xdmod, copied by curatrix new pcba. A job can name a variant (KiCad 10.0.8, KiCad spike §2.2), so the jobset holds one job per variant-dependent output and variant, copied from its base job except for the variant and file name; the variant names in the jobs equal those of the project. No “Execute Command” jobs, no “Copy Files” outside the output folder, no statistics job, BOM delimiters set, ERC and DRC not in the jobset (the checks evaluate them). curatrix fails the run when fewer jobs ran than the jobset has (a job KiCad cannot parse drops all jobs with exit code 0).

  • Outputs: Gerber and drill, pick-and-place, netlist, STEP, top and bottom renderings (orthographic) and one 3D rendering, schematic PDF and SVG, BOM CSV. The stackup table (and an optional SVG cross-section) and the design-rule table come from plain Python, because KiCad exports neither.

  • Where: output only under build/, never committed, no release asset, run only locally (no KiCad in CI). The bundle stays in iteration 2. KiCad batch runs use the workspace-local configuration, cache and documents folders, the C locale and a TMPDIR under build/, one after the other.

Per variant: set the variant row, recompute, export, close without saving; presence by Configs. The version comes from the assembly tags (Tags per board, assembly an... (XD-ADR-0140)), with the same preview marking as EE. A shared part from parts/ carries the version of the assembly being exported.

At export, and only there, curatrix embosses the short version (the full string goes into the drawing) with a font pinned in xdmod; the .FCStd stays unchanged, and the export fails unless the result is exactly one valid solid. GLB is deferred; renderings come at the end of Phase 5 (task 5.30). Output only under build/, only locally. Based on the FreeCAD spike (§5, §6).
Framework Decision: ME renderings without OpenGL, the fallback when Blender is absent XD-ADR-0147
status: valid
date: 2026-11-17
decision_status: proposed
refines: XD-ADR-0143
refined by: XD-ADR-0148

Proposed by the agent of task 5.30, for the owner to accept or change. The spike (claude/notes/me-renderings-spike.md) found that neither the Render workbench (an addon that needs an external renderer) nor a Coin3D snapshot (saveImage in the GUI binary offscreen gives a blank image; SoOffscreenRenderer finds no GL context) works headless. The owner first ruled out Blender, then allowed it as an optional local renderer (a separate change); this decision is the renderer curatrix cam uses when Blender is absent, and in every environment without it.

curatrix cam <repo> <asm> writes renderings/front|top|right|iso.png per variant from the same FreeCADCmd run (method zbuffer in cam.json): FreeCAD tessellates the present parts, the script draws the facets flat-shaded into a z-buffer (numpy, a dependency of FreeCAD) with the visible edges on top, and FreeCAD’s Qt writes the text and the PNG. The views are the ones of the drawing (right is the side view); front, top and right share one scale, iso has its own, and the scale is on each image. Colours come from the BOM kind, not from the document. Each image carries the assembly, the variant, the full version and the view, and PREVIEW unless a release; a rendering without a drawn facet, or a pinned font that does not load, fails the run.

Limits: orthographic and flat-shaded, no perspective, shadows or materials; where two parts overlap in one plane (a collision) the part drawn first shows, and edges that lie in another part’s face show through. Time grows with the drawn pixels and the facet count: 4 to 8 s per view for 272 000 facets (60 filleted tubes), about 1 s per view for a few boxes, on the owner’s machine, well inside the freecad limit of 10 minutes for a few variants.
Framework Decision: Blender as an optional local renderer of the ME renderings XD-ADR-0148
status: valid
date: 2026-11-17
decision_status: proposed
refines: XD-ADR-0147

Proposed by the agent of the Blender follow-up to task 5.30, for the owner to accept or change. The owner reversed “no Blender” on 2026-11-17: the Blender package of the machine may render, through its executable only (no bpy wheel, no new system package).

Optional and local. When blender is on the machine, curatrix cam <repo> <asm> lets FreeCADCmd write the tessellated parts per variant as glTF (<variant>.scene.glb beside cam.json; colour by BOM kind, as before) and Blender render the same four views (renderings/front|top|right|iso.png, same size, names and marking) with Cycles on the CPU: orthographic cameras, three sun lights and a dim sky, no shadows (overlapping or touching parts would shade each other black), Freestyle edges, fixed samples and seed, no denoiser, half the cores as threads (the output does not depend on the thread count). Without Blender, or with --no-blender, the z-buffer renderer of ME renderings without OpenG... (XD-ADR-0147) runs, so CI and machines without Blender get renderings too. cam.json says which: renderings.method is blender or zbuffer; for Blender also its version, engine, samples and seed.

Not pinnable. Blender comes from the distribution and curatrix installs nothing, so its output is never committed or compared, and tools.yaml records the version it was tried with (pinned: false): curatrix doctor notes a missing Blender and warns on another version, it never fails on them. Tests that need Blender are marked tools and run locally only.

Isolated. Every call, from curatrix, curatrix run -- blender, curatrix launch blender or the .venv/bin/blender shim, gets --factory-startup --offline-mode --disable-autoexec and the user paths under .xdmod/blender/ (BLENDER_USER_RESOURCES, _CONFIG, _SCRIPTS, _DATAFILES, _EXTENSIONS, the XDG dirs for the caches, TMPDIR), as KiCad and FreeCAD never run... (XD-ADR-0145) does for KiCad and FreeCAD; Blender’s Python runs without the workspace venv, and .xdmod/blender/bin (a copy of the shim) comes first on PATH, so a blender started by a child process is isolated too. Never call Blender bare. The blender limits (4 GB, 10 minutes per variant) apply, also to curatrix run -- blender without --use.
