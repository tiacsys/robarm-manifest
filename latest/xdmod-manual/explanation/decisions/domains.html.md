# Domain models and CAD

How the EE and ME repos refine the system model, which needs their models emit, and how KiCad
and FreeCAD files refer to them (Phase 5, task 5.14). Decisions that rest on the FreeCAD spike are
*proposed* until that spike is merged.

| **Conformance is a curatrix check, not a Pilot result.** The Pilot finds neither a missing<br/>redefinition nor a redefinition with the wrong port def. So curatrix checks, on the committed<br/>model JSON of the domain repo and its upstream: every port that a domain def inherits from a<br/>system def is redefined somewhere in the chain between the two, and the most specific<br/>redefinition’s def specializes the inherited port’s def. The same rule holds inside port defs at<br/>signal level. A variant def of a board does not repeat the redefinitions of its parent. An<br/>unsolved name clash of inherited ports is an error.<br/><br/>**Links come from specialization.** `curatrix gen model` turns a `:>` across the repo boundary<br/>into a trace link on the domain need, chosen by the pair of kinds: `EE-PCBA` / `ME-ASM` /<br/>`EE-HAR` to `SYS-EL` is `realizes`; `EE-PORT` / `ME-PORT` to `SYS-IF` is `conforms`.<br/>Any other pair is a finding, never skipped. A def without an ID of its own that specializes a<br/>system element is allowed only below the port level (for example a signal def inside a port def);<br/>anywhere else it is a warning. |
