curatrix Python API

curatrix is a Python package (xdmod/curatrix/src/curatrix). Other tools and tests may call these modules directly. Every subprocess must go through curatrix.limits.run(), so it gets the memory limit and timeout of its use. This page is generated from the docstrings.

Workspace and limits

The workspace: root discovery, repos, paths (command-layer.md §1, §5; repo-topology.md §2).

The workspace root is the west topdir (D67, D68). curatrix finds it itself, so commands also work from a subfolder:

  1. $XD_WORKSPACE if set;

  2. inside a worktree set (D125): the set root on the logical $PWD, also from a symlinked folder of the set (.worktrees/<branch>/zephyr);

  3. the nearest folder upward from the current directory that holds .west/;

  4. the folder above the xdmod checkout this package was installed from (editable install, <ws>/xdmod/curatrix/src/curatrix). This keeps curatrix usable before west init.

Memory limits and timeouts for every tool (D71, D117, command-layer.md §6).

limits.yaml (next to this package, xdmod/curatrix/limits.yaml) gives a memory limit and a timeout per use (docs, pilot, firefox, gui, …). <ws>/.xdmod/limits.yaml overrides it per use and key.

Backends ($XD_LIMIT_BACKEND forces one):

  • systemd: systemd-run --user --scope -p MemoryMax=M -p MemorySwapMax=0 -- timeout T cmd (the same as the interim xd-limit). Used when a systemd user session answers.

  • ulimit: sh -c 'ulimit -v KB; exec timeout T cmd' – GitHub runners have no systemd user session; the address-space limit is the fallback (vmem, default = memory).

  • none: no limits (debugging only).

GUI tools get a memory limit only (timeout: none, D117). Exit codes: the command’s own; 124 = timeout; 137 = killed (usually out of memory).

curatrix.limits.run(cmd, use='script', ws=None, *, memory=None, timeout=None, check=False, env=None, **kw)

subprocess.run under the limits of use. Extra keyword arguments go to subprocess.run.

IDs and the ledger

IDs and the ledger (id-scheme.md; D78, D79, D120, D128, D133).

Ledger <repo>/ids.yaml: every number ever issued, per kind, one per line, append-only:

# Every number issued per kind, one per line. Append-only: a number here is never issued again.
SYS-REQ:
  - 41
  - 42
SYS-NEED: []

A repo’s ledger lists the kinds it owns (a kind with no number yet is KIND: []). Placeholders <KIND>-NEW-<tag> (e.g. SYS-REQ-NEW-a) are replaced by curatrix ids fix; the same placeholder gets the same real ID in every file. SYS-VIEW is a reserved non-need kind (SysML view short names): issued from the ledger, skipped by CK-A3.

class curatrix.ids.Ledger(path: 'Path', kinds: 'dict[str, list[int]]'=<factory>)
issue(kind, used=frozenset({}))

Next number above everything in the ledger and in the sources; appended.

curatrix.ids.fix(repo, ledger, files=None, dry_run=False, exclude=())

Replace every placeholder in the repo’s text files with a newly issued ID. Returns {placeholder: new ID}. The same placeholder gets the same ID everywhere.

curatrix.ids.new(ledger, kind, repo, file=None, exclude=())

Issue one ID. With file, replace that file’s first placeholder of this kind.

curatrix.ids.check_ledger(files, ledger, root)

CK-C2: every ID of an owned kind in the sources is listed in the ledger (so the ledger is never behind the sources). Kinds the ledger does not own are upstream references.

Checks

curatrix check <repo> –stage local|pr|full|baseline [–no-cad] [–only …] [–json] (checks.md §3).

Runs the built-in checks a repo’s checks.yaml switches on, plus its commands, for one stage. Writes logs to build/<area>/checks/ and a summary JSON (build/<area>/checks/summary.json) for agents and CI comments, and prints the command that reproduces each failure.

Status of a check: pass | fail (error level: the stage fails) | warn | report | skip.

Graph rules on the merged needs of a docs build (trace-model.md §4; checks CK-A1, CK-A3, CK-B1-B3, CK-B5, CK-B6, CK-G1/G2). Only rules that need the merged graph live here: rules the sphinx-needs schema already enforces per document (orphans R3, HIL fields R5) were dropped (task 5.2, P4-9). sphinx-needs skips external needs in its own schema checks, so these run here over every needs.json of a build (own and imported needs alike).

Back links are computed here from the outgoing links (never trusted from the files). draft needs take part in structure checks but do not count as coverage (D130).

curatrix.graph.load(paths)

Merge the needs.json files of a build. Own needs win over imported copies.

Documents and generated files

curatrix docs <repo|full>: the zdocs build of a repo’s registry (D25, D35, D64c).

Output: build/<area>/docs/ (cmake binary dir); HTML, needs.json and objects.inv per document under build/<area>/docs/deploy/html/<doc-id>/ (doc-architecture.md §5). full builds the manifest repo’s registry into build/full/.

Strict (D64c): with a zdocs that knows ZDOCS_STRICT (zdocs PR #36) curatrix passes -DZDOCS_STRICT=ON; otherwise -W –keep-going and ninja -k 0, so every document reports.

Generated, committed files (“generate, commit, check”, spike lesson 2).

Each generator computes the file content in memory. curatrix gen writes it; curatrix check compares it with the committed file (CK-D1, CK-D2, CK-D4). All paths come from checks.yaml.
